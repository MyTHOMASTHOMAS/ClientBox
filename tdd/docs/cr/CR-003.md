## 2. Questions posées et réponses obtenues

| ID | Question posée | Réponse |
|---|---|---|
| **CR-03/Q01** | Quelle est la source de configuration par défaut chargée au runtime ? | Le fichier **`env/.env`** (relatif au répertoire de travail / workspace). |
| **CR-03/Q02** | Que se passe-t-il si le fichier par défaut `env/.env` n'existe pas sur le disque ? | **Ce n'est pas une erreur.** L'application reste résiliente, n'émet pas d'erreur de fichier manquant et s'appuie directement sur les variables d'environnement déjà présentes dans le processus (`process.env` du shell OS, conteneur Docker, CI). |
| **CR-03/Q03** | Comment spécifier un fichier d'environnement alternatif en ligne de commande ? | Via les options de démarrage **`-e <chemin>`** ou **`--env <chemin>`** (ainsi que la syntaxe pointée **`--env=<chemin>`**). |
| **CR-03/Q04** | Que se passe-t-il si un fichier est explicitement spécifié via `-e` ou `--env` mais que ce fichier est inexistant ? | **Arrêt fatal immédiat.** Une erreur explicite en français est levée (`EnvLoadError` / `ServerCliParseError`) indiquant que le fichier spécifié est introuvable, car l'opérateur a expressément demandé un chemin invalide. |
| **CR-03/Q05** | Doit-on implémenter une cascade multi-fichiers complexe (`.env.local`, `.env.test`, `.env.production`) ? | **Non.** Aucune cascade complexe n'est implémentée. La configuration provient soit du fichier explicite (`-e`), soit du fichier par défaut (`env/.env`) s'il existe, complété par `process.env`. |
| **CR-03/Q06** | Quels binaires CLI d'agents et variables sont obligatoires au runtime ? | Les **trois binaires CLI d'agents embarqués** (**`CURSOR_CLI_BIN`**, **`ANTIGRAVITY_CLI_BIN`** et **`CODEX_CLI_BIN`**) sont **tous obligatoires** au démarrage. Leur chemin doit pointer vers un fichier existant et exécutable sur le système hôte, sous peine d'arrêt fatal immédiat avec renvoi explicite vers `env/.env.example`. |
| **CR-03/Q07** | Quel est l'impact sur le pipeline de build Vite (`ADR-008`) ? | **Suppression totale de l'injection statique `define`** de variables d'environnement au build. Le livrable `dist/clientsbox.js` devient 100 % autonome, portable et dynamique. Le build réussit même si aucun fichier d'environnement n'est présent sur la machine de compilation. |
| **CR-03/Q08** | Comment ce mécanisme résout-il le dysfonctionnement de `LOGS_DISABLED=true` ? | En chargeant l'environnement de manière synchrone dès les toutes premières lignes d'exécution de `clientsbox.js`, `LOGS_DISABLED=true` est injecté dans `process.env` avant toute émission de log, garantissant le silence total des sorties console. |
| **CR-03/Q09** | Quel est le rôle du service d'initialisation applicatif ? | Centraliser le chargement, l'injection dans `process.env`, la **validation stricte des 3 binaires obligatoires**, l'assignation des **valeurs par défaut** pour les options non renseignées (`PORT=2974`, `HOST=127.0.0.1`, `AGENTS_DIR=.agents`, `LOGS_DISABLED=false`, etc.), et l'arrêt propre avec message clair si un prérequis fait défaut. |

## 3. Ce que nous n'avons pas demandé

- Le rechargement à chaud des variables d'environnement sans redémarrer le processus Node.js (un redémarrage du processus reste la norme en cas de modification de configuration).
- Le chiffrement ou masquage automatique des secrets dans la mémoire du processus Node.js.
- La prise en charge de formats de configuration alternatifs (YAML, TOML ou JSON) pour les variables d'environnement.

---

## 4. Reformulation

Le client formalise une refonte architecturale majeure de la gestion des variables d'environnement pour assurer la portabilité complète du livrable `dist/clientsbox.js` et garantir le pilotage dynamique du comportement applicatif (notamment le kill-switch des logs) :

### 1. Abandon du « Baking » Vite au Build
* Suppression de l'injection en dur via `define` dans `vite.config.ts`.
* Le build produit un binaire JavaScript neutre, découplé de la machine qui le compile.

### 2. Chargement Dynamique au Runtime
* **Par défaut :** Recherche du fichier `env/.env`. S'il est absent, l'application poursuit son amorçage sans lever d'erreur de fichier en utilisant l'environnement existant (`process.env`).
* **Explicite :** Prise en charge des flags CLI `-e <chemin>` / `--env <chemin>` / `--env=<chemin>`. Si le fichier indiqué n'existe pas, l'application échoue immédiatement avec un message clair.

### 3. Service de Validation et Valeurs par Défaut
* Validation des exécutables obligatoires : les 3 binaires CLI d'agents (**`CURSOR_CLI_BIN`**, **`ANTIGRAVITY_CLI_BIN`**, **`CODEX_CLI_BIN`**) sont **obligatoires au runtime** (contrats REQ-031 / REQ-112 / ADR-003). Échec explicite si l'un d'eux est manquant, vide ou non exécutable, avec renvoi vers `env/.env.example`.
* Application des valeurs par défaut pour les options non renseignées (`PORT`, `HOST`, `AGENTS_DIR`, `LOGS_DISABLED`, `CALL_SCENARIO_MAX_DEPTH`, timeouts).
* Injection effective dans `process.env` avant l'initialisation du logger, rendant opérationnel `LOGS_DISABLED=true`.
