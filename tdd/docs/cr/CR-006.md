## 1. Ce que le client a dit

> « ### 1. Image Docker de base (Dockerfile)  
> L'image commune repose sur node:24-slim (ou node:24 pour embarquer d'office les outils de compilation et Python) et répond aux contraintes de démarrage de ClientsBox :  
> * Variables d'environnement intégrées (ENV) : HOST=0.0.0.0 (obligatoire dans Docker, la valeur par défaut étant 127.0.0.1), PORT=2974, AGENTS_DIR=.agents, et les chemins des 3 binaires obligatoires (CURSOR_CLI_BIN, ANTIGRAVITY_CLI_BIN, CODEX_CLI_BIN). Comme ClientsBox tolère l'absence de env/.env et bascule sur process.env, aucun fichier .env n'est requis dans le projet.  
> * Emplacement des binaires CLI : installés dans /usr/local/bin/ ou /opt/ (jamais dans /root, afin de ne pas être masqués par le volume d'authentification).  
> * Workspace et point d'entrée : WORKDIR /workspace (car ClientsBox ancre workspacePath sur process.cwd()) et ENTRYPOINT ["node", "/opt/clientsbox/clientsbox.js"].  
> * Support git et scripts .sh : sh/bash sont déjà présents dans node:24-slim pour les blocs Command (exécutés dans le workspace), mais git (ainsi que curl, jq, openssh-client, ca-certificates) doit être ajouté via apt-get, suivi de git config --system --add safe.directory '*'. »  

> « ### 2. Authentification partagée (zéro reconnexion)  
> Pour éviter de reconnecter les CLI à chaque projet, les jetons stockés dans $HOME (/root) sont isolés dans un volume Docker nommé partagé entre tous les conteneurs :  
> 1. Création unique : docker volume create clientsbox-cli-auth.  
> 2. Connexion unique : lancement d'un conteneur temporaire (docker run --rm -it --entrypoint bash -v clientsbox-cli-auth:/root ...) pour authentifier les 3 CLI, puis exit.  
> 3. Réutilisation : montage de -v clientsbox-cli-auth:/root sur chaque lancement (en external: true dans Docker Compose). »  

> « ### 3. Les deux modes de déploiement  
> * Mode 1 — Par projet (docker-compose.yml commité) : la racine du projet est montée sur /workspace, le dossier .agents (versionné dans Git) est utilisé directement ou via AGENTS_DIR, et le volume clientsbox-cli-auth est déclaré en external: true. Toute l'équipe partage les mêmes workflows.  
> * Mode 2 — Global (script wrapper --rm) : plutôt qu'un conteneur unique persistant (qui ne permet pas de changer les volumes -v à chaud), un script global lance un conteneur éphémère --rm en montant dynamiquement le workspace, le dossier .agents et le volume d'auth. Chaque exécution est isolée (et pour éviter que les CLI tiers ne confondent le chemin /workspace, il suffit de monter le projet sur son vrai chemin hôte : -v "$WS:$WS" -w "$WS"). »  

> « ### 4. Exécution non interactive (--exec-scene)  
> L'ajout de --exec-scene <id|nom> à la commande Docker lance directement le mode headless (streaming console sans serveur HTTP) en conservant les codes de sortie (0 succès, 1 erreur, 130 Ctrl+C) :  
> * Sans TTY : retirer -it (ou utiliser -T avec docker compose run --rm -T).  
> * Gestion des signaux : ajouter --init (ou init: true en Compose) pour que Ctrl+C (SIGINT) tue proprement les sous-processus enfants et renvoie 130.  
> * Sans port exposé : ne pas mapper -p 2974:2974 en mode --exec-scene afin d'éviter tout conflit si l'UI web tourne déjà ou si plusieurs scénarios tournent en parallèle. »  

> « ### 5. Outils spécifiques et personnalisation utilisateur  
> * Commits / push Git par les agents : Monter ~/.gitconfig et ~/.ssh en :ro. Forcer les fins de ligne LF (*.sh text eol=lf) dans .gitattributes pour les utilisateurs Windows.  
> * Ajouter des outils durables (python3, php, make…) : Image dérivée (FROM mon-org/clientsbox:latest) via un Dockerfile.clientsbox.  
> * Test rapide sans Dockerfile : Conteneur persistant (sans --rm, avec --name + docker exec). »

## 3. Ce que nous n'avons pas demandé

- La modification du code applicatif interne TypeScript (ClientsBox résout nativement ses variables au runtime depuis `process.env` en l'absence de fichier `env/.env` grâce à ADR-022 ; impact `src/` = 0 ligne).
- Le déploiement sur un cluster Kubernetes ou Swarm multi-nœuds (le périmètre est expressément centré sur Docker et Docker Compose mono-hôte).
- L'inclusion de secrets, de jetons ou de clés d'API en clair dans l'image Docker (l'image reste totalement agnostique et neutre, les jetons restent confinés dans le volume nommé hôte).
- La compilation de binaires spécifiques au runtime Docker (ClientsBox utilise son livrable universel portable `dist/clientsbox.js`).
- La publication automatisée des images sur un registre public comme Docker Hub (la construction reste locale ou gérée par la CI privée de l'organisation).
- L'adoption du conteneur persistant comme mode d'exploitation standard (réservé aux tests exploratoires jetables).

## 4. Reformulation

Le client demande la formalisation et la livraison d'un **environnement de déploiement conteneurisé Docker officiel** pour ClientsBox, articulé autour de cinq piliers directeurs :

### 1. Image Docker de base reproductible et outillée
* Image fondée sur `node:24-slim` intégrant les dépendances système (`git`, `curl`, `jq`, `ca-certificates`, `openssh-client`).
* Neutralisation de l'erreur Git sur volumes montés via `git config --system --add safe.directory '*'`.
* Installation automatisée des **4 binaires obligatoires** via leurs pipelines d'installation officiels curl (`cursor`, `claude`, `antigravity`, `codex`).
* Sanctuarisation des exécutables sous `/usr/local/bin/` (`cursor-agent`, `claude`, `agy`, `codex`) et variables d'environnement associées : `CURSOR_CLI_BIN`, `ANTIGRAVITY_CLI_BIN`, `CODEX_CLI_BIN`, `CLAUDE_CLI_BIN`.
* Variables d'environnement standardisées : `HOST=0.0.0.0`, `PORT=2974`, `AGENTS_DIR=.agents`.
* Point d'entrée direct sur le livrable universel : `ENTRYPOINT ["node", "/opt/clientsbox/clientsbox.js"]`.

### 2. Gestion centralisée de l'authentification (Zéro reconnexion)
* Isolation des tokens CLI (`$HOME`) dans le volume Docker nommé persistant `clientsbox-cli-auth` monté sur `/root`.
* Procédure de login unique via un conteneur éphémère interactif, puis réutilisation transparente pour tous les projets.

### 3. Deux modes d'exploitation officiels et gestion des tests rapides
* **Mode 1 — Projet (`docker-compose.yml`)** : situé à la racine du projet, dédié aux équipes, montant le workspace, persistant les ressources `.agents/` et liant le volume d'authentification externe.
* **Mode 2 — Global (Script wrapper CLI)** : exécution éphémère isolée (`--rm`) montant le workspace sous son chemin absolu réel (`-v "$WS:$WS" -w "$WS"`) pour préserver la cohérence des références de chemins dans les LLM.
* **Usage exploratoire ponctuel** : utilisation tolérée d'un conteneur persistant sans `--rm` (`docker exec`), classée hors standard de production.

### 4. Support complet du mode non interactif (`--exec-scene`)
* Exécution headless sans serveur web et sans mapping de port.
* Utilisation systématique de `--init` pour la gestion propre des interruptions (`SIGINT` $\rightarrow$ code `130`).

### 5. Extensibilité et outillage spécifique
* Modèle d'images dérivées pour les dépendances métiers tierces (`Dockerfile.clientsbox`).
* Recommandations de montage pour l'identité Git (`.gitconfig`, `.ssh:ro`) et normalisation des fins de ligne LF (`*.sh text eol=lf`).
